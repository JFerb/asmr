## Package Organization

- The overhead of a ROS package is not large. Define separate packages wherever they make sense. Often, code can be useful in contexts other than those for which it was built.
- Avoid combining nodes that pull in mutually unneeded dependencies and are often used separately (to eliminate unnecessary build overhead).
- The package dependency graph must be acyclic, i.e. no package may depend on another that directly or indirectly depends on it.
- If programs with similar dependencies are generally used together, consider combining them into a single package.
- If some nodes have common dependencies on shared code that you do not wish to export publicly, they can be combined internally within a single package.
- **Create separate packages that contain only messages, services and actions (separation of interface and implementation).** Examples for separate message packages are the [ros/common_msgs](https://github.com/ros/common_msgs) packages.
- Group packages in stacks.

## Package Naming

Refer to [REP-144: ROS Package Naming](https://ros.org/reps/rep-0144.html) and [ROS 2 Naming Conventions](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-ROS-2-Subscriptions.html).

Choose the name carefully:

- They are messy to change later.
- Package names are global to the entire ROS ecosystem.
- Try to pick names that will make sense to others who may wish to use your code.
- Package names should be specific enough to identify what the package does. Do not over scope, e.g. *planner* is a bad name, use *wavefront_planner* instead.
- Do not use “utils” or other catchalls. 
- Prefixing a package name is recommended ***only*** when the package is not meant to be used more widely (e.g., packages that are specific to the StlarETH robot use the ‘starleth_’ prefix).

## Naming Conventions for Packages, Nodes, Topics, Services, TF etc.

Adapted from [ROS Best Practices: Lorenz Mösenlechner, Technische Universität München, July 2012](http://robohow.eu/_media/meetings/first-integration-workshop/ros-best-practices.pdf):

- Package names are lower case.
- Packages must not contain dashes (“-”), only underscores (“_”).
- Nodes, topics, services, actions, parameters are all lower case with underscores as separator.
- Messages, services and actions are named in camel case: `geometry_msgs/PoseStamped`.
- Names in a message/service/action definition are all lower case with underscores as separator: `geometry_msgs/Pose end_effector`.
- Do not use the word “action” in an action definition: `Foo.action`, not `FooAction.action`.

## Custom ROS Message and Services

- **Use standard data types whenever possible (try to prevent `.msg` proliferation)!** For example, instead of creating a custom `EstimatorUpdateTime.msg`, use the [`std_msgs/Time`](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-ROS-2-Services.html) message. Another example is an empty service call, use [`std_srvs/Empty`](https://github.com/ros2/common_interfaces/blob/master/std_srvs/srv/Empty.srv) instead.
- **Do not define a new msg/srv/action definition for each topic/service/action!** For example, instead of creating two  definitions `LoadMapFromFile.srv` and `SaveMapToFile.srv` with the same content

		string file_path
		—

	define one type ‘ProcessFile.srv’ which can be used from both services, `~/load_map` and `~/save_map`, respectively.
- Complex messages are built through composition (e.g. [`geometry_msgs/PoseWithCovarianceStamped`](https://github.com/ros2/common_interfaces/blob/master/geometry_msgs/msg/PoseWithCovarianceStamped.msg)).
- Try to avoid building messages that tend to not get completely filled out.

References:

- [common_interfaces](https://github.com/ros2/common_interfaces)

## Topics vs Services vs Actionlib vs Parameters vs Dynamic Parameters

Refer to [ROS 2 Patterns - Communication](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-ROS-2-Services.html).

Summary:

- Use topics for publishing continuous streams of data, e.g. sensor data, continuous detection results, …
- Use services only for short calculations.
- Use actions for all longer running processes, e.g. grasping, navigation, perception, …
- Use parameters for values which are known at launch and are not likely to change during run time.
- Use dynamic parameters (`dynamic_reconfigure`) for parameter which are likely to change during run time.

## Node Initialization

In ROS 2, nodes are created directly using the `rclcpp::Node` (C++) or `rclpy.node.Node` (Python) class.

All communication (publishers, subscribers, services) is created within the node's context.

### C++ Example:

```cpp
#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

class MyNode : public rclcpp::Node {
public:
  MyNode() : Node("my_node") {
    publisher_ = this->create_publisher<std_msgs::msg::String>("topic_name", 10);
  }
};
```

### Python Example:

```python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class MyNode(Node):
  def __init__(self):
    super().__init__('my_node')
    self.publisher_ = self.create_publisher(String, 'topic_name', 10)
```

## Namespacing

Topic names are resolved relative to the node's namespace. Use relative topic names for internal communication and never use absolute names (`/topic`).

**Good**: `odometry`, `grid_map`, `cam0/camera_info`  
**Bad**: `/odometry`, `/grid_map`, `/helicopter/cam0/camera_info`

## Topic Naming

Topics should be named in the context of the node. Very simple and clear names are preferred for a easy to understand “ROS API”. Topic names not cause collision as long as they are published within the namespace of the node (see *Namespace for Topics and Parameters*).

In ROS 2, topic remapping is done in launch files (Python-based) or via command-line arguments using the `--ros-args` syntax.

References:

* [When Topics Should be Remapped (ROS1)](http://wiki.ros.org/ROS/Patterns/Communication#When_Topics_Should_be_Remapped)

## Parameter Naming

Use a hierarchical scheme for parameters, such as

	camera/left/name: left_camera
	camera/left/exposure: 1
	camera/right/name: right_camera
	camera/right/exposure: 1.1

instead of 

	camera_left_name: left_camera

etc. This protects parameter names from colliding and allows parameters to be access individually or as a tree. In a YAML-file, the structure would be

	camera:
	  left:
	    name: left_camera
	    exposure: 1
	  right:
	    name: right_camera
	    exposure: 1.1

References:

* [ROS 2 Parameter Server](https://docs.ros.org/en/jazzy/Concepts/Basic.html#parameters)

## Parameter Organization

For ROS 2, parameters are typically set using Python-based launch files (`.launch.py`). Create parameter files in YAML format and load them in the launch file.

### Example Launch File (`my_node.launch.py`):

```python
from launch import LaunchDescription
from launch_ros.actions import Node
from launch.substitutions import LaunchConfiguration
from launch.actions import DeclareLaunchArgument
import os
from ament_index_python.packages import get_package_share_directory

def generate_launch_description():
  config_dir = os.path.join(
    get_package_share_directory('my_package'),
    'config')
  
  default_param_file = os.path.join(config_dir, 'robot_params.yaml')
  
  declare_param_file = DeclareLaunchArgument(
    'params_file',
    default_value=default_param_file,
    description='Full path to the ROS 2 parameters file')
  
  return LaunchDescription([
    declare_param_file,
    Node(
      package='my_package',
      executable='my_node_exec',
      name='my_node',
      output='screen',
      parameters=[LaunchConfiguration('params_file')]
    )
  ])
```

Parameter files use YAML format:

```yaml
my_node:
  ros__parameters:
    camera:
      left:
        name: left_camera
        exposure: 1
      right:
        name: right_camera
        exposure: 1.1
```

## Using Third-Party Libraries

Encourages standalone libraries with no ROS dependencies. Don’t put ROS dependencies in the core of your algorithm!

If you can develop a ROS independent library and release a parallel ROS wrapper

https://web.archive.org/web/20200331162114/courses.csail.mit.edu/6.141/spring2012/pub/lectures/Lec06-ROS.pdf

Refer to [ROS 2 Package Dependencies](https://docs.ros.org/en/jazzy/How-To-Guides/Ament-CMake-Doc.html).

- If possible, try to use libraries from Debian packages.
- Specify rosdep dependencies (tool for installing system packages).
- If you need to compile a library from source create a ROS wrapper package that downloads and compiles the package.
- Don’t use sudo in wrapper packages.
- Don’t require manual system wide installations.
- Don’t copy libraries into packages that need them.

## Dependencies

Keep your dependencies clean:

- Only depend on what you need,
- Specify all dependencies,
- Do not use implicit dependencies.

**If multiple runs of `colcon build` are required for your workspace to be built, something is fishy!**

## Startup Order

In ROS 2, do not require a specific startup order for nodes. Use appropriate wait mechanisms:

### C++:
```cpp
// Wait for a service to be available
auto client = this->create_client<MyService>("service_name");
while (!client->wait_for_service(std::chrono::seconds(1))) {
  if (!rclcpp::ok()) {
    RCLCPP_ERROR(this->get_logger(), "Service not available");
    return;
  }
  RCLCPP_INFO(this->get_logger(), "Waiting for service...");
}
```

### Python:
```python
# Wait for a service
client = self.create_client(MyService, 'service_name')
while not client.wait_for_service(timeout_sec=1.0):
  if not rclpy.ok():
    self.get_logger().error('Service not available')
    return
  self.get_logger().info('Waiting for service...')
```

* [ROS 2 Client Libraries](https://docs.ros.org/en/jazzy/Concepts/Intermediate/About-Client-Libraries.html)

## Launch File Organization

For larger projects with many nodes, organize your launch files modularly in the `launch/` directory of your package.

### Example structure:
```
my_package/
├── launch/
│   ├── full_system.launch.py      # Main entry point
│   ├── perception.launch.py        # Perception nodes
│   ├── control.launch.py           # Control nodes
│   └── tools.launch.py             # Debugging/visualization tools
├── config/
│   ├── perception.yaml
│   ├── control.yaml
│   └── ...
└── ...
```

### Including other launch files:
```python
from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
from ament_index_python.packages import get_package_share_directory
import os

def generate_launch_description():
  perception_launch = IncludeLaunchDescription(
    PythonLaunchDescriptionSource(
      os.path.join(
        get_package_share_directory('my_package'),
        'launch', 'perception.launch.py')))
  
  control_launch = IncludeLaunchDescription(...)
  
  return LaunchDescription([perception_launch, control_launch])
```

## Printing Messages/Logging

In ROS 2, use the ROS 2 logging system via `rclcpp` (C++) or `rclpy` (Python).

### C++:
```cpp
#include "rclcpp/rclcpp.hpp"

// Logging levels: DEBUG, INFO, WARN, ERROR, FATAL
RCLCPP_DEBUG(this->get_logger(), "Debug message");
RCLCPP_INFO(this->get_logger(), "Info message with param: %d", value);
RCLCPP_WARN(this->get_logger(), "Warning message");
RCLCPP_ERROR(this->get_logger(), "Error message");
RCLCPP_FATAL(this->get_logger(), "Fatal message");
```

### Python:
```python
import rclpy

self.get_logger().debug('Debug message')
self.get_logger().info(f'Info message with param: {value}')
self.get_logger().warning('Warning message')
self.get_logger().error('Error message')
self.get_logger().critical('Critical message')
```

Best Practices:

- Use appropriate logging levels (don't overuse DEBUG or INFO for production code)
- Provide introspection/debug topics for visualization of internal state
- Use `--log-level` argument to control logging verbosity at runtime

* [ROS 2 Logging Documentation](https://docs.ros.org/en/jazzy/Tutorials/Logging.html)

## Checking the Number of Subscribers

To avoid computational overhead for topics which no nodes are subscribed to, check the number of subscribers in ROS 2:

### C++:
```cpp

```

### Python:
```python
if self.publisher_.get_subscription_count() < 1:
  return
```

		ros2 bag record <topic> <topic> ...

## Converting Between ROS Messages and Other Types

### Eigen

To convert to/from messages, use **[geometry_msgs](https://github.com/ros2/common_interfaces/tree/master/geometry_msgs)** with **[Eigen](http://eigen.tuxfamily.org/)** (C++) or **NumPy** (Python).

**C++ Example:**

```cpp
#include "Eigen/Core"
#include "geometry_msgs/msg/point.hpp"

Eigen::Vector3d my_vector(1.0, 2.0, 3.0);
geometry_msgs::msg::Point point_msg;
point_msg.x = my_vector(0);
point_msg.y = my_vector(1);
point_msg.z = my_vector(2);
publisher_->publish(point_msg);
```

**Python Example:**

```python
import numpy as np
from geometry_msgs.msg import Point

my_vector = np.array([1.0, 2.0, 3.0])
point_msg = Point()
point_msg.x = float(my_vector[0])
point_msg.y = float(my_vector[1])
point_msg.z = float(my_vector[2])
publisher_.publish(point_msg)
```

To go to/from TF, use **[tf2](https://docs.ros.org/en/jazzy/Tutorials/Intermediate/Tf2/Tf2-Main.html)** library:

**C++ Example:**

```cpp
#include "tf2/LinearMath/Quaternion.h"
#include "geometry_msgs/msg/transform_stamped.hpp"

tf2::Quaternion quaternion;
quaternion.setRPY(0, 0, 0);
geometry_msgs::msg::TransformStamped transform;
transform.header.frame_id = "map";
transform.child_frame_id = "world";
transform.header.stamp = this->now();
transform.transform.translation.x = 1.0;
transform.transform.translation.y = 2.0;
transform.transform.translation.z = 3.0;
transform.transform.rotation.x = quaternion.x();
transform.transform.rotation.y = quaternion.y();
transform.transform.rotation.z = quaternion.z();
transform.transform.rotation.w = quaternion.w();
tf2_broadcaster_->sendTransform(transform);
```

**Python Example:**

```python
from geometry_msgs.msg import TransformStamped
from tf_transformations import quaternion_from_euler

quaternion = quaternion_from_euler(0, 0, 0)

transform = TransformStamped()
transform.header.frame_id = "map"
transform.child_frame_id = "world"
transform.header.stamp = self.get_clock().now().to_msg()
transform.transform.translation.x = 1.0
transform.transform.translation.y = 2.0
transform.transform.translation.z = 3.0
transform.transform.rotation.x = quaternion[0]
transform.transform.rotation.y = quaternion[1]
transform.transform.rotation.z = quaternion[2]
transform.transform.rotation.w = quaternion[3]
tf_broadcaster.sendTransform(transform)
```

### OpenCV Image

Use **[cv_bridge](https://github.com/ros-perception/vision_opencv/tree/ros2/cv_bridge)** for ROS 2 to convert between ROS messages and OpenCV images.

**C++ Example:**

```cpp
#include "cv_bridge/cv_bridge.h"
#include "sensor_msgs/msg/image.hpp"

void image_callback(const sensor_msgs::msg::Image::SharedPtr msg) {
  cv_bridge::CvImagePtr cv_ptr;
  try {
    cv_ptr = cv_bridge::toCvCopy(msg, "bgr8");
  } catch (cv_bridge::Exception& e) {
    RCLCPP_ERROR(this->get_logger(), "cv_bridge exception: %s", e.what());
    return;
  }
  cv::Mat image = cv_ptr->image;
}

void publish_image(cv::Mat& image) {
  cv_bridge::CvImage cv_image;
  cv_image.header.frame_id = "camera";
  cv_image.header.stamp = this->now();
  cv_image.encoding = "bgr8";
  cv_image.image = image;
  publisher_->publish(*cv_image.toImageMsg());
}
```

**Python Example:**

```python
from cv_bridge import CvBridge
from sensor_msgs.msg import Image
import cv2

bridge = CvBridge()

def image_callback(msg):
  try:
    cv_image = bridge.imgmsg_to_cv2(msg, "bgr8")
  except Exception as e:
    self.get_logger().error(f"cv_bridge exception: {e}")
    return
  # Process cv_image (numpy array)

def publish_image(cv_image):
  msg = bridge.cv2_to_imgmsg(cv_image, "bgr8")
  msg.header.frame_id = "camera"
  msg.header.stamp = self.get_clock().now().to_msg()
  publisher_.publish(msg)
```

## Colcon Build Configuration

ROS 2 uses `colcon` instead of `catkin`. Here are useful build configurations:

```bash
# Standard build
colcon build

# Build specific package
colcon build --packages-select my_package

# Build with release mode (optimized)
colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release

# Build with debug symbols
colcon build --cmake-args -DCMAKE_BUILD_TYPE=Debug

# Build with verbose output
colcon build --verbose

# Build with specific number of jobs
colcon build --parallel-workers 4
```

You can also create a `.colcon` configuration file in your workspace root to persist these settings.

* [Colcon Documentation](https://colcon.readthedocs.io/en/released/)
